Let the AI write slop Keep it in buckets

AI agents keep the architecture explicit in buckets.config.json, and every agent inherits the decisions of the ones before it. The file lists the buckets, which are groups of files with one job each, what each one does, and which buckets and npm packages each one imports and why. Hooks stay silent while the code follows it. When an edit makes the code diverge, the hook offers the agent a fix in the code and a fix in the config. Both fixes are valid, and no human approves anything.

Why

An AI agent solves each task by the shortest path, and the shortest path is usually an import from some other part of the project. After a few hundred tasks, every module depends on every other module.

Each agent starts without knowing why the code looks the way it does. slopbuckets writes those decisions into buckets.config.json, next to the code, and its hooks compare every edit with that file. The next agent reads the reasons instead of guessing them.

No human approves anything. An agent may fix the code or change the architecture, and both are valid answers to a warning. The hooks only make sure that the code and the config never drift apart without the agent hearing about it.

Nx module boundaries, eslint-plugin-boundaries, Sheriff and dependency-cruiser also check which part of a project may import which. Their rules use tags or patterns, a human changes them, and they report in the editor or in CI. slopbuckets has one entry with a reason for each dependency, lets the agent change it, and reports inside the agent at each edit. It is not an ESLint plugin, and it checks TypeScript and JavaScript only. If you know another tool compares them one by one.

The config holds the decisions Every agent keeps code and config in sync

How it works

01 Buckets

A bucket is a set of files with one job. Globs pick its files, and a glob that starts with ! leaves some out. Every file belongs to exactly one bucket or matches ignore, which keeps tests, scripts and tool configs out of the architecture. Each bucket has 5 required fields:

  • purpose, one line that says what the bucket does
  • files, the globs of its files
  • public, the file or list of files other buckets may import, or null when the bucket exports nothing
  • dependsOn, the buckets it may import, each with a one-line reason
  • packages, the npm packages and Node built-ins it imports, each with a one-line reason

Nothing is implicit. A file in no bucket, a file in two buckets and a glob that matches nothing are all reported.

// buckets.config.json
{
  "version": "2.0",
  "ignore": ["**/*.test.ts", "scripts/**"],
  "projects": ["packages/sdk"],
  "buckets": {
    "billing": {
      "purpose": "Issues and charges invoices",
      "files": ["src/billing/**", "!src/billing/stripe/**"],
      "public": "src/billing/index.ts",
      "dependsOn": {
        "payments": "Charges go through the gateway",
        "log": "Logs failed charges with the invoice id"
      },
      "packages": {
        "zod": "Validates the invoice payloads of the public API"
      }
    },
    "payments": {
      "purpose": "Talks to the payment gateway",
      "files": ["src/payments/**"],
      "public": "src/payments/index.ts",
      "dependsOn": {},
      "packages": {}
    }
  }
}

Part of a config. Paths are relative to the file, and the reasons are what the next agent reads.

02 Dependencies

dependsOn lists the buckets a bucket may import, each with a one-line reason. An import of a bucket that is not listed is an undeclared dependency, and a listed bucket that no file imports is an unused one.

There is no wildcard. A log bucket that 50 buckets use needs 50 entries, and each one says why that bucket logs. The config may not declare a cycle, and code can only follow declared dependencies, so the code has no cycle between buckets either.

packages works the same way for code outside the project. Every npm package and Node built-in a bucket imports, such as zod or node:fs, needs an entry with a reason, type-only imports included.

Other buckets import only the public files. They hold named re-exports and nothing else, so they are the interface of the bucket. A name they export that no other bucket imports is reported, which keeps the interface small.

// src/payments/index.ts, the public file of payments
export { charge } from './client';
export type { Charge } from './types';

// src/billing/invoice.ts
import { charge } from '../payments';

billing imports payments through its public file, and the dependencies of billing say why.

03 Hooks

buckets init installs hooks in your coding agent. They print nothing while the code follows the config, so they cost no tokens. When the code diverges, the agent gets the list of pending items with every tool call until the list is empty:

  • before an edit, the hook simulates it in memory and warns about what it would break
  • before any other tool, the hook repeats the list: a new item in full once, then as a one-line reminder
  • at the end of the turn, the hook runs the full check and blocks once if anything is left

Every item ends with what to do, as a fix code line, a fix config line, or both. With both, a choose one fix: line above them says that they are alternatives and the agent picks one.

buckets: 2 pending. Fix the code or edit buckets.config.json. Either is valid. Full detail: buckets check

[NEW]
billing -> log: undeclared dependency
src/billing/refund.ts:2 imports logError from src/log/index.ts
billing: Issues and charges invoices
log: Formats and writes application logs
app depends on log: Logs errors thrown during startup
choose one fix:
fix code: remove the import by moving the code that needs it into log, or by moving what it uses from log into billing
fix config: add "log": "<one-line reason>" to buckets.billing.dependsOn

[OLD]
src/utils/date.ts: in no bucket

[RESOLVED]
billing -> payments: private file (src/billing/refund.ts:1)

What the hook adds to the agent's context at the third edit of a session on the sample project. The first edit imported a private file of payments, the second created src/utils/date.ts, and the third replaced the private import with one of the public file and added an import of log. The line about app shows why another bucket already depends on log. The hooks guide lists every message.

tty5rules18 checks

$ buckets check

What the check enforces

  1. buckets.config.json is valid JSON with every required field, no empty purpose or reason, no unknown bucket in dependsOn and no package named by a subpath, such as lodash/merge. While it is invalid no other rule runs, so the hook refuses an edit that makes it worse: a config problem that was not there, or more problems than before. A config that is already broken shows its problems in the pending list. config-invalid
  2. The dependsOn graph of the config has no cycle. config-cycle
  3. A file of bucket A imports bucket B only when the dependsOn of A lists B. dependency-undeclared
  4. Every bucket that A lists in dependsOn is imported by some file of A. dependency-unused
  5. Every npm package and Node built-in that a file of a bucket imports is listed in its packages, and every listed package is imported. package-undeclared package-unused
  6. Other buckets import only the public files of B, and no file of B when its public is null. import-private
  7. A relative import, an import that matches a paths pattern of tsconfig.json and an import of a workspace package resolve to a file. import-unresolved
  8. Every file that public lists exists and belongs to the bucket. public-missing
  9. A public file holds only named re-exports: no code, no export * and no re-export from another bucket. public-not-interface
  10. Every name a public file exports is imported by another bucket. Tests and ignored files do not count, and a bucket with external is exempt. export-unused
  11. A file of a bucket does not import a file that ignore lists. import-ignored
  12. import() and require() take a string literal, so the check can see what they load. import-dynamic
  13. import * as x, export * from and import() without destructuring do not point to another bucket, because they hide which names the code uses. import-namespace
  14. Every file is in a bucket or in ignore. file-unowned
  15. No file is in two buckets. A file that ignore matches leaves the architecture first, so it never conflicts with a bucket. file-overlap
  16. Every glob of files and ignore, and every folder of projects, matches something. glob-empty
  17. Every nested buckets.config.json is listed in projects. project-undeclared

Every rule id, with what it means and how to fix it, is in the rules reference.

A pending item makes the check exit with code 1. It prints every item in full, the same text the stop hook gives the agent. Here an agent added src/billing/refund.ts, which imports a private file of payments, and src/utils/date.ts, which no bucket owns.

Warn or interrupt

Before a tool runs, every rule only warns. At the end of a turn, every rule blocks once. The one exception is config-invalid. The hook refuses an edit that adds a config problem, or more problems than the config had, because with an unreadable config the other rules cannot run. A config that is already broken shows in the pending list instead.

Inspect

buckets inspect serves a read-only page on 127.0.0.1 for the human who checks what the agents did. Every element on it answers a question: what the architecture is, what is pending now, why one bucket depends on another, where a file lives and what changed while you watched. Every selection goes into the URL, so the back button works and a link opens the same view.

What the page shows

Graph
The buckets in layers, dependents above their dependencies. A solid line is a dependency that is declared and used, a dashed line is declared but unused, and a red dotted line is an import without a declaration. Above 60 buckets, the graph opens focused on one bucket and its neighbors.
Matrix
Bucket by bucket, with the number of imports in each cell. It stays readable with hundreds of buckets.
Pending
Everything buckets check reports, grouped by rule or by bucket. It opens first when something is pending.
Files
The file tree with the bucket of each file, or ignored, no bucket or two buckets.
Panel
For the selection: the purpose, the globs, each export of the public file and who imports it, the dependencies with their reasons and the imports behind each one.
Export
--export svg, mermaid, dot or html prints the graph, or the whole page as one file that works without a server, and exits.

In the terminal

buckets inspect --json prints the snapshot the page draws from and exits: projects, buckets, dependencies with their imports, exports and pending items. Agents and scripts read it instead of the page.

The page updates while files change and marks what changed since you opened it: a new bucket, a dependency added or removed, a new pending item. The marks go away when you click seen or reload. The history lives in git.

The inspect guide covers the views, the panel and the keyboard, and the snapshot reference describes the JSON.

Nested projects

A monorepo can hold several projects, each with its own buckets.config.json. The config around them lists their folders in projects, and their files leave the outer project, so every file answers to one config.

  1. buckets check checks the current project and every project it lists, recursively. --no-recursive checks only the current one.
  2. A buckets.config.json in a folder that projects does not list is reported by project-undeclared. A listed folder without a config is reported by glob-empty.
  3. A pending item of a nested project starts with its folder, such as packages/sdk: , so the agent knows which config to edit.
  4. When the public file of a bucket is the entry of an npm package, the bucket declares external with a reason. export-unused then stops asking for consumers inside the repository.
// packages/sdk/buckets.config.json
{
  "version": "2.0",
  "buckets": {
    "client": {
      "purpose": "Typed client for the public API",
      "files": ["src/**"],
      "public": "src/index.ts",
      "dependsOn": {},
      "packages": {},
      "external": "Entry point of the npm package"
    }
  }
}
packages/sdk/buckets.config.json: nested project not listed in projects
choose one fix:
fix code: delete packages/sdk/buckets.config.json if it is not a project
fix config: add "packages/sdk" to projects

Windsurf gets one hook, which refuses an edit that breaks the config and shows no pending list. Zed, Continue and other agents get no hooks and follow the AGENTS.md block. After the edit means the agent takes no context before a tool runs, so the warning arrives with the result of the edit. An agent whose stop cannot block relies on the AGENTS.md block, which tells it to run buckets check before it finishes, and on the git pre-commit hook from buckets init --git-hook. Without a compaction event, the agent keeps getting one-line reminders after a compaction. Supported agents explains each partial and unverified cell and has a page per agent. For Claude Code, buckets init installs one PreToolUse hook with the matcher *, which runs for every tool, and one hook each for Stop, SubagentStop and PostCompact:

HookWhat it does
PreToolUse on Write, Edit, NotebookEdit and MultiEditSimulates the edit in memory and adds the pending list to the context. When the hook cannot compute the new text, as for NotebookEdit, it adds the current list and marks the session as one that changed files. It refuses the edit only when the edit makes buckets.config.json worse, with a config problem that was not there or more problems than before.
PreToolUse on every other toolAdds the same pending list without simulating anything. A Bash or PowerShell command marks the session as one that may have changed files.
StopRuns the full check when the session changed files or still has pending items, and blocks once with every pending item in full.
SubagentStopDoes the same at the end of each subagent, and the text goes to the subagent.
PostCompactForgets which items the session already showed in full, so the next pending list shows them in full again.

These hooks never answer allow, so the permission prompts of Claude Code stay as they are. With nothing pending, they print nothing. The hooks guide has the details.

What the check sees. slopbuckets checks imports. Two buckets that share a database table, an event topic, an environment variable or an injection token are coupled without an import, and the check cannot see that. One bucket with src/** passes every rule and says nothing about the architecture. Read what the check guarantees.

Install

npm install -g slopbuckets 
$ npm install -g slopbuckets
$ cd your-project
$ buckets init     # empty config, hooks, AGENTS.md block and skill
$ buckets check    # every file is in no bucket until the agent maps it

buckets init writes an empty config, with "version": "2.0", "buckets": {}, "ignore": [] and "projects": []. It installs the hooks of your agent, the AGENTS.md block and the skill, a Markdown file that teaches the agent to edit the config. It adds .buckets/ to .gitignore, a folder that holds the cache of the check and the session state of the hooks. It also sets up a git merge driver, so two branches that each add a bucket merge without a conflict.

Right after init, the check reports every file as in no bucket, grouped by folder. Then ask your agent to build the first architecture. The getting started guide has a prompt for that.

In CI, add slopbuckets as a dev dependency, so every machine runs the same version, and run the check on every pull request. It exits with 1 when the code and the config differ, whoever wrote the change, and with 64 when the command line is wrong:

$ npm install --save-dev slopbuckets
$ npx buckets check

Before you adopt it

  • every bucket lists every npm package and Node built-in it imports, with a reason
  • every dependency between buckets is its own entry with a reason, so a log bucket used by 50 buckets needs 50
  • imports of private files move to public files, and buckets fix import-private rewrites them
  • the install is about 24 MB, nearly all of it TypeScript 6, or about 48 MB next to a project's own TypeScript 5
  • a pull request that changes the architecture changes buckets.config.json, and buckets check --base main lists those changes with their reasons

The costs of adoption has the details and what each cost buys.

Install with your AI agent

Paste this prompt into Claude Code or another coding agent, opened in your project folder. The agent reads llms.txt and follows its install steps.

Install slopbuckets in this project and build its first architecture. Read https://nicolascaous.github.io/slopbuckets/llms.txt and follow the steps for agents.
  1. Checks that Node.js is version 20 or newer, installs the CLI with npm install -g slopbuckets and runs buckets --version.
  2. Checks for tsconfig.json and creates one when it is missing.
  3. Runs buckets init --agent <name> with its own name, such as claude or codex, or --agent auto when it is not one of the supported agents.
  4. Reads the code and writes the first buckets in buckets.config.json, with a purpose for each bucket and a reason for each dependency.
  5. Runs buckets check after each change until it exits with 0, then shows you the config with a short summary.

Then read the config it wrote. Every decision in it is one line that you or the next agent can change.
