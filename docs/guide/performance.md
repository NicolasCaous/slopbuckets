# Performance

The pre-edit and pre-tool hooks run before every tool call of the agent, so they must finish fast enough that nobody notices them. The check gets there by never loading the TypeScript type checker and by keeping what it learned in a cache.

## What the check needs

The check needs three things: the list of files, the imports of each file and the file each import points at. It never reads types.

- A light scanner extracts `import`, `export ... from`, `import()` and `require()` without loading TypeScript.
- Each file resolves its imports with the nearest `tsconfig.json` at or above it inside the project. Relative imports, `paths` and `baseUrl` resolve against the file list without touching the disk, and Node built-ins and npm packages are recognized by name. TypeScript loads only for workspace packages and for `#` imports without a `paths` entry, and its answers stay in the cache.
- The file list comes from `git ls-files -co --exclude-standard`, or from a walk of the folders outside a git repository.

## The cache

The cache lives in `.buckets/cache/`, which `init` adds to `.gitignore`. It holds:

- for each file, its modification time, its size and its imports
- the resolutions already made, by folder and specifier
- the hashes of the resolution inputs and of `buckets.config.json`

The resolution inputs are every `tsconfig.json` the resolver read, with its `extends` chain, `package.json`, `pnpm-workspace.yaml`, the `package.json` of each workspace package and of the TypeScript in use, and the marker files that npm, pnpm and yarn write into `node_modules` at each install. A change to any of them drops the cached resolutions, because module resolution may differ. So an install after the first check, which links workspace packages into `node_modules`, makes the next check resolve every import again. A change to `buckets.config.json` drops nothing: the rules run again on the import graph, which did not change. A cache written by another CLI version, or deleted in the middle of a session, is rebuilt.

## What each hook reads

- pre-edit reads the cache, scans only the edited file with the new content from the hook input, and runs every rule on the cached import graph with that file replaced, so it gives what `buckets check` would give once the edit lands. When the edit leaves the imports, exports and type names of the file as they were, the rules would see the same graph, so pre-edit takes the result the cache holds for that graph and runs only the checks that read the disk. It also looks at the folder of the edited file on disk, so a file that a shell command wrote, moved or deleted there counts too. A shell change in another folder counts from the next stop: checking every folder would cost 60 to 120 ms at 10,000 files.
- pre-tool simulates nothing. It shows the last known pending list, after it checks the modification time of the files those violations name. After a shell command, which can change any file, the pre-tool and pre-edit lists say under their header that they may miss problems the command caused, until the stop checks every file. A full check takes about 150 ms at 10,000 files, twice the pre-tool budget.
- stop updates the cache with everything that changed since the last run, including files a shell command moved, and runs the rules on the whole graph.

Times include starting Node. A run over budget fails the benchmark job in CI.

| stop, warm cache, 1,000 files changed | 10,000 files | under 1 s | 299 / 318 ms, 302 / 314 ms |
| `buckets check`, cold | 10,000 files | under 2 s | 907 / 938 ms, 1,021 / 1,035 ms |

The measured column gives the median and the p95 of two runs of `npm run bench`, 15 samples each, every sample a new Node process as a hook runs it. The machine: Windows 11 Pro, an Intel Core i9-13900KF (24 cores, 32 threads), 32 GB of memory, NVMe disks, Node 24.12.0, git 2.55 and Windows Defender real-time protection on. The CPU load was under 10% before the first run and between 23% and 29% before the second, from other programs. The 50,000-file rows come from two later runs, with the CPU load under 6% before each. The 10,000-file project has 10,013 files and the 50,000-file project 50,014, both with 500 buckets, generated by `scripts/stress-project.mjs` with the presets `10k` and `50k`.

Most of a pre-tool call is Node itself: an empty script takes about 35 ms to start on this machine, and the CLI adds about 15 ms to load. A pre-edit at 50,000 files spends about 8 ms reading the 12 MB cache. The rules take about 13 ms more when the edit changes an import, an export or a type name. A stop spends most of its time waiting for `git ls-files` and `git status`.

`buckets inspect --json` prints 6.4 MB of JSON at 50,000 files, and writing it to a pipe takes about 150 ms of that time.

Inside the inspect server, the file watcher names the files that changed, and the engine reads only those files instead of running `git status` and `git ls-files`. A new snapshot after one file changed takes about 25 ms at 50,000 files, against about 180 ms with the full listing, and the server writes the cache 250 ms after the snapshot goes out. The full listing still runs when a change is a folder, a `.gitignore`, a `tsconfig*.json`, a `package.json` or a `buckets.config.json`, when a new file differs from a known one only in case, and when the watcher reports an event without a file name. It also runs 5 seconds after each burst of changes, so a change the watcher missed shows on the page within 5 seconds.

| Scenario | Measured |
|---|---|
| `buckets inspect`, one file written to the end of the snapshot event at the server, 50,000 files | 88 / 129 ms |

That time covers the 25 ms the server waits for more changes, the snapshot and sending 6.4 MB. One run of 15 samples.

The inspect page has budgets of its own: the first screen in under 1 second with 500 buckets and 50,000 files, any click answered in under 100 ms, and a live update shown in under 200 ms. In headless Chromium on the same machine, a source edit at 50,000 files shows on the page, from the file write to the painted frame, in 120 ms median and 169 ms at most over 40 edits. Before the engine read only the changed files, the same edit took 356 ms median. An edit that lands while the 5-second full snapshot runs waits for it, which adds up to about 200 ms.

## How it is measured

`scripts/bench.mjs` runs each scenario 15 times and reports the median and the p95 as JSON. The projects come from a generator with a fixed seed, so every run measures the same code:

- repositories of 1,000, 10,000 and 50,000 files
- 500 buckets with globs that exclude each other
- a deep graph (a chain of 50 buckets) and a wide one (one bucket that 300 depend on)
- one file of 20,000 lines with 400 imports
- a `tsconfig.json` with many `paths` and a chain of `extends`
- npm and pnpm workspaces with symlinks
- paths with spaces and uppercase letters on Windows
- a nested project

The hook scenarios add a burst of 50 parallel edits that share the session state file, a long session with 200 pending violations, a stop after a shell refactor that moves 1,000 files, a config edit that changes 100 dependencies at once, a cache deleted mid-session and a cache from an older CLI.

CI runs the benchmark on Linux and Windows on every pull request. The job fails when a budget is exceeded, or when a median gets more than 20% slower than `bench/baseline.json`, the baseline kept in the repository. `bench/baseline.json` has no entries for Linux or Windows yet, so only the budgets apply. A baseline has to come from the same hardware as the runner that compares against it, and medians recorded on a developer machine make every scenario fail on a CI runner. The runners are noisy, so a failure counts only when a second run confirms it. Only the Linux job fails on a budget, because Node starts too slowly on the Windows runner, where the benchmark runs with `--report-only` and fails only when a scenario errors or hangs.
